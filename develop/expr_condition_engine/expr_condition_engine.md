# 条件表达式引擎

在"[第八章 BFE的路由转发机制](../../design/route/route.md)"中介绍过，BFE的分流转发规则及各扩展模块的规则，都通过"条件（Condition）"来描述请求匹配逻辑。本章介绍自v1.9.0引入的条件表达式引擎（bfe_expr）：它与原条件引擎双轨并存，在保持存量配置完全兼容的前提下，大幅扩展了条件的表达能力。

## 背景

BFE原有的条件体系基于goyacc语法解析器，内置60余个固定搭配的条件原语（如`req_path_in()`、`req_header_in()`等），原语之间仅支持`&&`/`||`/`!`布尔组合。这一设计简单可靠，但有明显的表达能力上限：

- 新增一个匹配维度，必须修改Go代码、增加新的原语；
- 无法表达算术计算、数值区间、多值谓词等逻辑；
- 规则之间无法传递中间结果。

## 双引擎架构

条件表达式引擎基于[expr-lang/expr](https://expr-lang.org/)构建，作为第二引擎与原引擎双轨并存。全部条件的消费方（路由表及各mod_*模块的规则）经统一的`condition.Build`入口分派，模块侧不需要任何改动。

配置加载期的处理流程如下：

- 按进程级模式开关（`bfe.conf`中`[Server]`段的`ConditionEngineMode`）分派：
  - `LegacyFirst`（默认）：先由旧引擎解析；旧引擎解析失败（新风格表达式或新旧混写）才改用expr引擎；
  - `ExprCompatible`：expr引擎 + 旧原语名自动重写（新旧可混写）；
  - `ExprOnly`：纯expr引擎，旧原语名视为普通函数。
- 旧原语不做字符串层的自动翻译，而是"函数化兼容"：每个旧原语实现为表达式环境`Env`的一个方法，在类型检查前由`legacyPatcher`把原语名重写为方法名。
- 表达式在配置加载期完成编译（`expr.Compile` + 完整类型检查）：类型错误、未知函数、结果非bool都在加载期暴露为配置错误，而不是运行期故障。

运行期每个请求构造一次表达式环境（`NewEnv(req)`，缓存于请求上下文），同一请求内所有条件与动作参数表达式共享该环境，保证用户变量读写、随机源等语义"每请求一致"。

## 表达式环境

表达式可用的取数函数按子环境组织：

| 子环境 | 能力 |
| --- | --- |
| BaseEnv | 请求/响应/会话/路由/后端地址等基础取数（ReqPath()、ReqHeader()、ResCode()等） |
| TimeEnv | 当前时间与时间区间判断（Now()、InTimeRange()等） |
| HashEnv | 哈希与网段判断（Hash()、IpIn()、Rand()等） |
| VarEnv | 用户变量读写（UsrVarSetInt()、UsrVarGetStr()等），存于请求级Context，可跨规则、跨模块传递 |
| RedisEnv | 表达式内读Redis（见下文"动态数据源"） |
| InnerEnv | 既有`%变量`内置变量的函数化形式 |
| LegacyEnv | 全部旧条件原语的同名方法 |

求值约定：

- 条件表达式结果必须为bool；取数函数数据缺失时返回零值（空串/0/空列表），不视为错误；
- 运行期求值出错时，该条规则条件按false处理并输出warn日志（含logid与表达式串），不影响其他规则与请求处理；
- 条件表达式允许受控副作用（如`UsrVarSetInt("k", v); false`形式的序列表达式）。规则按配置顺序求值、每条规则的条件在一次请求中至多求值一次，因此"前排种子规则写变量、后续规则读变量"是可靠的跨规则传递机制。

## 动作参数表达式

v1.9.0起，部分模块的动作参数支持以`=`前缀内嵌表达式，在请求处理时动态计算参数值。参数写法分三态：

| 写法 | 语义 |
| --- | --- |
| `=expr` | 表达式，结果必须为string；加载期编译与类型检查，失败即配置加载失败 |
| `==lit` | 转义字面量（`==foo`表示字面值`=foo`） |
| 其他 | 普通字面量，原样使用，零开销 |

已支持的消费点：共享动作（mod_rewrite、mod_prison）中除Header名以外的参数位；mod_redirect的`URL_SET`/`URL_PREFIX_ADD`；mod_header的Header值参数。表达式求值失败的参数按空串处理并输出warn日志，不阻断同一动作的其他参数与后续动作。

例如，以下重写规则把请求Host动态改写为"原始Host加固定后缀"：

```json
{
    "Cmd": "HOST_SET",
    "Params": ["=req_host() + '.inner.example.com'"]
}
```

## 动态数据源

表达式引擎支持在表达式内读取外部数据源：

- **Redis**（已可用）：`GetRedisClient(addr)`按地址返回进程级单例client（默认超时conn 100ms / read 300ms / write 300ms），支持`Get`/`GetInt`/`HGetAll`读操作。访问超时或出错时按零值返回（不报错、不重试），避免故障放大。
- **HTTP服务、全局变量、配置表**：接口已定义（HttpEnv/GlbEnv/ConfEnv），当前版本为stub实现——调用输出warn并返回零值，后续版本逐步开放。

需要注意：表达式内的Redis读是同步网络IO，会占用处理该请求的协程，使用时应评估QPS与Redis容量；Redis地址直接写在表达式内，意味着规则配置的作者需要被信任。

## 模式开关与迁移

`ConditionEngineMode`在`bfe.conf [Server]`段配置，默认`LegacyFirst`：此模式下存量配置行为与旧版本完全一致（旧引擎解析成功即按旧语义执行），可以零风险升级后逐步试用新表达式；新风格配置则自动落到expr引擎。模式变更需重启进程，热加载不改变模式。

新旧引擎存在少量有意为之的语义差异（如字符串转义规则统一为Go语义、`res_code_in`为字符串比较而新式`ResCode()`为整数比较等），默认模式下不受影响；在`ExprCompatible`/`ExprOnly`模式下迁移存量配置时需留意这些差异。
